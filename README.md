# بازوی گزارش مواد / تاندیش (بله)

ربات پیام‌رسان **بله** برای دریافت **سه فایل Excel مشخص**، اعمال کنترل دسترسی نقش‌محور (RBAC)، **تحلیل مصرف مواد تاندیش**، و تولید **گزارش PDF ترکیبی**. رابط کاربری فارسی است.

## استانداردهای کارخانه برای نوع تاندیش

این سامانه دقیقاً سه نوع تاندیش را به‌عنوان استاندارد کارخانه می‌پذیرد (برای «موجودی روزانه سایت» و مصرف ماهانه):

- `slab` — **تاندیش اسلب**
- `bloom` — **تاندیش بلوم**
- `billet` — **تاندیش بیلت**

در Excel می‌توان کلید انگلیسی یا برچسب فارسی را وارد کرد؛ هنگام بارگذاری هر سه به برچسب فارسی استاندارد تبدیل می‌شوند.

## اهداف محصول

1. **تشخیص مقدار مواد مصرفی روزانه** — میانگین مصرف روزانه هر ماده / تاندیش از فایل موجودی روزانه سایت (و در صورت نبود، تقریب از مصرف ماهانه ÷ ۳۰).
2. **پیشنهاد درخواست مواد توسط ربات** —  
   `suggest_qty = max(0, forecast_need − remaining_inventory)`
3. **گزارش مقدار مواد مصرفی بر حسب زمان درخواستی** — امروز / ۷ روز / ۳۰ روز یا  
   `از YYYY-MM-DD تا YYYY-MM-DD`
4. **مواد بحرانی** — `days_of_cover = remaining / avg_daily < CRITICAL_DAYS` (پیش‌فرض ۳).
5. **پیش‌بینی نیاز** — `forecast_need = avg_daily × requested_days`
6. **گزارش مواد مازاد** — موجودی خیلی بیش از نیاز کوتاه‌مدت (جزئیات پایین).

برای استقرار روی VPS / سرور لینوکس، از اسکریپت یک‌مرحله‌ای استفاده کنید:

```bash

# سپس در ترمینال واقعی (ویزارد توکن و نام کاربری ربات):
cd special-materials-robot-project && bash install.sh
```

یا:

```bash
git clone https://github.com/silent4time/special-materials-robot-project.git
cd special-materials-robot-project
bash install.sh                 # ویزارد فارسی: توکن + نام کاربری ربات + اختیاری systemd
```

اولین کسی که در بله `/start` بزند **مالک** می‌شود؛ دانستن `ADMIN_BALE_USER_ID` از قبل لازم نیست.
جزئیات، پرچم‌ها (`--update` و …) و هشدار «فقط یک نمونه polling»: **[DEPLOY.md](DEPLOY.md)**.

## دستیار هوشمند (محلی)

از منوی تحلیل، «🤖 دستیار هوشمند» را باز کنید (**همه نقش‌ها به‌جز تکنسین**). پاسخ‌ها فقط از زمینهٔ **گزارش‌های محلی** ساخته می‌شوند و از **Ollama روی سرور** (پیش‌فرض مدل `qwen2.5:3b`) می‌آیند — **بدون API ابری**.

| موضوع | توضیح |
|--------|--------|
| دامنه | فقط گزارش‌ها (مصرف، موجودی، بحرانی، مازاد، پیش‌بینی، ورودی، فعالیت، …) |
| نقش‌ها | مالک / مدیر / کاردان مسئول — تکنسین دسترسی ندارد |

| امنیت | فقط HTTP محلی به Ollama؛ توکن و داده به ابر LLM نمی‌رود |

## گزارش هدف اصلی

منو: **گزارش‌ها / تحلیل تاندیش** → **🎯 گزارش هدف اصلی** (مالک / مدیر / کاردان مسئول؛ حذف ماه: مالک / مدیر). وب: `/reports/main-goal`.

### مرحله ۱ — سابقهٔ ماهانه (حداقل ۳ ماه توصیه می‌شود)

هر ماه = چهار فایل Excel با **بازهٔ یکسان**:

1. آمار تولید (نگاشت CCM: CCM1/2=اسلب، CCM3=بلوم، CCM4/5=بیلت)
2. مصرف تاندیش بیلت
3. مصرف تاندیش بلوم
4. مصرف تاندیش اسلب

- **📤 آپلود ۴ فایل یک ماه**: ترتیبی؛ بازه از نام فایل / شیت / سربرگ خوانده می‌شود و اگر یکسان نباشد «بازه زمانی فایل‌ها یکسان نیست» و ماه ذخیره نمی‌شود.
- **📦 آپلود گروهی چند ماه**: همهٔ فایل‌ها به هر ترتیب؛ نوع فایل و ماه خودکار تشخیص داده می‌شود (نام پیشنهادی: «آمار تولید شهریور ۱۴۰۵.xlsx»، «مصرف تاندیش بیلت شهریور ۱۴۰۵.xlsx»)؛ هر ماهی که ۴ فایلش کامل شود ذخیره می‌شود.
- ماه‌ها جداگانه در جدول `main_goal_months` ذخیره می‌شوند (آپلود دوبارهٔ همان ماه = جایگزینی). با کمتر از ۳ ماه هشدار داده می‌شود ولی محاسبه انجام می‌شود.

### مرحله ۲ — سناریوها (خروجی PDF + اکسل)

- **🎯 سناریو ۱: تناژ هدف** — بازه (مثلاً «۳ ماه»، «مهر ۱۴۰۵») + بخش (بیلت/بلوم/اسلب/کل) + تناژ → تاندیش لازم ≈ تناژ ÷ (تن بر تاندیش تاریخی)، مواد ≈ نرخ بر تن × تناژ، مقایسه با موجودی منبع اصلی و ظرفیت ماهانهٔ سابقه. «کل» به نسبت سهم تاریخی بخش‌ها تقسیم می‌شود.
- **🔮 سناریو ۲: پیش‌بینی N ماه آینده** — روند خطی تناژ ماهانهٔ هر بخش (≥۳ ماه؛ وگرنه میانگین) → تناژ، تاندیش و مواد لازم هر بخش.

منطق مشترک: `services/main_goal_report.py` (تشخیص بازه/نوع فایل، تجزیه) و `services/main_goal_history.py` (سابقه، نرخ‌ها، سناریوها، خروجی).

## یادآور گزارش‌های ورودی الزامی

بله: **⚙️ تنظیمات ربات → 🔔 یادآور گزارش‌های الزامی**؛ وب: `/settings/reminders` (فقط مالک / مدیر).

- دریافت‌کنندگان: نقش‌ها (مالک/مدیر/کاردان مسئول/تکنسین) و/یا کاربران خاص.
- زمان‌بندی: روز مهلت (فایل‌های هر ماه تا روز X ماه بعد)، چند روز قبل از مهلت، تکرار عقب‌افتاده (هر N روز)، ساعت ارسال (تهران)، تعداد ماه‌های الزامی اخیر.
- ربات (`main.py`) هر ~۶۰ ثانیه `services/mandatory_reminders.tick` را اجرا می‌کند؛ پیش‌فرض **غیرفعال** است تا مالک/مدیر روشنش کند. «ارسال همین حالا» در وب فقط پرچم می‌گذارد و ربات آن را می‌فرستد.

## گزارش تاندیش بعد از ریخته‌گری

منطق مشترک ربات و وب: `services/tundish_report.py` (اعتبارسنجی، تجزیهٔ متن، ذخیره)؛
UX ربات: `bot/tundish_report_flow.py`؛ وب: `/tundish-report` و `/tundish-report/settings`.

- **ورود (همه نقش‌ها: مالک، مدیر، کاردان مسئول، تکنسین):** منوی اصلی → «🧾 گزارش تاندیش بعد از ریخته‌گری»
  → «🧾 گزارش تاندیش اسلب/بلوم/بیلت» → «✍️ ورود مرحله‌ای» یا «📋 ورود سریع از متن» → خلاصه → «✅ تأیید و ثبت گزارش» (یا «✏️ اصلاح یک مورد»).
- **فیلدهای ثابت:** شماره تاندیش، خط/ماشین (اسلب ۱/۲ = CCM1/2، بلوم = CCM3، بیلت ۱/۲ = CCM4/5 — قابل تنظیم)، سکوئنس، تعداد ذوب، مارک.
- **اقلام قابل تنظیم (choice / number / text):** اسلب — نازل (وضعیت/ذوب تعویض/علت)، شرود (وضعیت/سازنده)، پودر قالب، پودر تاندیش؛
  بیلت و بلوم — علت پایان سکونس، نوع ایمپکت، مدت ریخته‌گری (دقیقه).
- **تنظیمات (مالک/مدیر):** «⚙️ تنظیمات گزارش تاندیش» (در منوی گزارش تاندیش و «⚙️ تنظیمات ربات») → «⚙️ اقلام گزارش …» → افزودن / ویرایش (برچسب، نوع، گزینه‌ها، اجباری، ترتیب) / حذف / خطوط.
- **ذخیره:** `tundish_reports` (فیلدها + JSON اقلام + متن خام + ثبت‌کننده + زمان UTC و تهران) و `tundish_report_values` (نرمال‌شده).
- تست: `python scripts/smoke_tundish_report.py`

## منبع اصلی (شکل Excel — موجودی انبار ورودی)

> **قانون معماری:** جدول تمیز `product_inventory` («منبع اصلی») منبع **اصلی و کانونی**
> داده‌های اصلی انبار برای ربات و وب است. همیشه از **آخرین استخراج**
> (`get_latest_extracted` / مسیر clean) خوانده می‌شود — نه از مسیرهای کهنهٔ جلسه.
>
> - آپلود «منبع اصلی» و هر فایل «مواد مصرفی» با همین قالب
>   (`category_code, id, product_name, keyword, usage_location, quantity, priority`) این جدول را به‌روز می‌کند.
> - گزارش‌های انبار/کارخانه (مازاد، پیشنهاد، پیش‌بینی، درخواست مواد، ورودی انبار)
>   حقایق موجودی را از این جدول (+ ledger) می‌گیرند.
> - «موجودی و مواد بحرانی» ترجیحاً از `site_stock_entries` (موجودی روزانه سایت)
>   می‌خواند؛ در نبود سایت، به منبع اصلی برمی‌گردد.
> - ماژول مشترک: `analytics/frames.py` (ربات + وب).


### فایل خام (آپلود)

حداقل **۳ ستون** با سرصفحه‌های فارسی (یا معادل انگلیسی)؛ ستون «کلید واژه» اختیاری است:

| ستون فارسی | کلید داخلی | توضیح |
|------------|------------|--------|
| کد دسته بندی | `category_code` | عدد ۴ رقمی |
| کد و شرح کالا | `item_code_desc` | متن شامل شناسه + شرح (فقط برای پارس؛ در خروجی تمیز ذخیره نمی‌شود) |
| موجودی | `quantity` | مقدار موجودی |
| کلید واژه | `keyword` | اختیاری — اگر نباشد در تمیز خالی می‌ماند |

### استخراج شناسه (`id`) و خروجی تمیز

**فرض پیش‌فرض** (قابل تنظیم در `excel/id_parse.py` تا وقتی کاربر فرمت نهایی را تأیید کند):

> از ابتدای «کد و شرح کالا»، اولین توکن شامل رقم (و حروف اختیاری) را قبل از اولین فاصله، خط تیره فاصله‌دار ` - `، یا خط تیره en `–` بردار.

نمونه‌ها:

- `ACID01 - اسید سولفوریک` → `id=ACID01` ، `product_name=اسید سولفوریک`
- `55 ماده` → `id=55` ، `product_name=ماده`

خروجی تمیز (`product_inventory`) ستون‌های زیر را دارد (بدون متن ترکیبی خام):

`category_code`, `id`, `product_name`, `keyword`, `quantity`, `priority`

`product_name` برای اتصال به نام ماده در مصرف روزانه/ماهانه استفاده می‌شود.

### فیلتر و اولویت

1. فقط ردیف‌هایی که `category_code` در جدول `category_codes` (لیست مجاز) باشد نگه داشته می‌شوند.
   کد **۱۸۰۰** مخصوص **اقلام مازاد** است و در لیست پیش‌فرض (`DEFAULT_CATEGORY_CODES`) همیشه هست تا هنگام آپلود منبع اصلی حذف نشود.
2. ستون `اولویت` / `priority`؛ خانه خالی = **۱** (بالاترین). `priority == 0` یعنی «بدون اولویت»: ردیف ذخیره می‌شود ولی در پیشنهاد درخواست مواد / درخواست مواد استفاده نمی‌شود.
   ستون «سطح ریخته گری» (`casting_floor`) جای «سایر نواحی» (`other_areas`) را گرفته؛ فایل‌های قدیمی خودکار منتقل می‌شوند.
   فقط شیت «ریز اطلاعات» نگه داشته می‌شود (Sheet1 / کل موجودی / Sheet3 از فایل ذخیره‌شده حذف می‌شوند).
   پیمانکار/شرکت: در شناسه مواد پیمانکار، چهار رقم دوم از چپ `0000` است (`excel/id_parse.py`).
3. شناسه نامعتبر / موجودی غیرعددی حذف می‌شود.
4. نسخه تمیز در `uploads/<user>/<session>/cleaned/product_inventory.xlsx` و رکورد در `extracted_datasets` ذخیره می‌شود.
5. اگر لیست مجاز خالی باشد، ربات می‌گوید ابتدا از منو کد دسته اضافه کنید.

### جدول `category_codes`

| فیلد | نوع |
|------|-----|
| `code` | TEXT UNIQUE — دقیقاً ۴ رقم |
| `label` | اختیاری |
| `active` | پیش‌فرض ۱ |
| `created_at` / `created_by` | زمان و کاربر ثبت‌کننده |

کدهای پیش‌فرض (`DEFAULT_CATEGORY_CODES`) هنگام bootstrap در دیتابیس seed می‌شوند؛ می‌توان از منوی ربات کدهای بیشتری اضافه کرد. کد **۱۸۰۰** با برچسب **اقلام مازاد** رزرو شده است.

## گزارش مواد مازاد

تعریف عملیاتی (در متن UI فارسی هم آمده):

- کد دسته **۱۸۰۰** → همیشه اقلام مازاد (دلیل: «کد دسته ۱۸۰۰ — اقلام مازاد»)، **یا**
- `days_of_cover > max(CRITICAL_DAYS × 3, SURPLUS_COVER_DAYS)` (پیش‌فرض پوشش > ۱۰ روز وقتی CRITICAL_DAYS=۳)، **یا**
- موجودی بیش از نیاز پیش‌بینی‌شده برای `SURPLUS_FORECAST_DAYS` روز (پیش‌فرض ۳۰)، **یا**
- موجودی دارد ولی مصرف متناظر ثبت نشده → پرچم **«مازاد/بدون مصرف»**.

## نقش‌ها (RBAC)

| نقش | دسترسی |
|-----|--------|
| مالک / مدیر | همه ردیف‌ها + مدیریت کاربران + تنظیمات اقلام |
| کاردان مسئول | همه ردیف‌ها (مثل مالک/مدیر برای فیلتر داده) + تنظیمات اقلام سایت؛ هویت = شناسه بله |
| تکنسین | فقط ورود تعاملی «موجودی روزانه سایت» (سه گروه)؛ بدون تنظیمات/گزارش؛ فیلتر assignee در صورت وجود ستون |

شناسایی افراد با `bale_user_id` است. هر ورودی داده ثبت‌کننده را ذخیره می‌کند (`bale_user_id` / `created_by` / `assigned_by`). ستون `scope` برای سازگاری قدیمی نگه داشته شده و برای کاردان مسئول الزامی نیست.

**منبع اصلی** ستون domain/assignee ندارد → برای همه کاربران مجاز **قابل مشاهدهٔ کامل** است (plant-wide). موجودی روزانه سایت دیگر Excel تکنسین نیست.

### موجودی روزانه سایت (ورود تعاملی)

مسیر اصلی تکنسین/کاربران: منو → سه گروه → ورود مقدار یکی‌یکی. داده در SQLite ذخیره می‌شود.

| جدول | نقش |
|------|-----|
| `catalog_items` | فهرست اصلی اقلام (`id`, `name_desc`, `category_code`, `active`) — از استخراج منبع اصلی seed می‌شود |
| `catalog_group_assignments` | تخصیص یک گروه به هر قلم: `slab` / `bloom` / `billet` |
| `site_stock_entries` | موجودی روزانه؛ upsert یکتا بر `(entry_date, tundish_group, item_id)`؛ فیلدهای `quantity` + `pallet_qty`/`unit_qty`/`quantity_detail` برای توسعه بعدی |

برچسب‌های منو: **موجودی مواد اسلب** / **موجودی مواد بلوم** / **موجودی مواد بیلت**.

نمونه Excel قدیمی `01_tank_consumption.xlsx` هنوز برای تحلیل مصرف تاریخی/آفلاین موجود است؛ مسیر UI تکنسین دیگر آپلود آن نیست.


پس از ثبت موفق، در صورت تنظیم گروه گزارش، خلاصه به گروه بله ارسال می‌شود:

1. ربات را به گروه اضافه کنید و `/set_stock_group` بفرستید (مالک/مدیر)، یا
2. `SITE_STOCK_REPORT_GROUP_ID` در `.env`، یا از «تنظیمات ربات» → «گروه گزارش موجودی روزانه».

بدون شناسه، ثبت موجودی بدون خطا ادامه می‌یابد.

## محدودیت‌ها

- فرمت دقیق شناسه در «کد و شرح کالا» هنوز توسط کاربر نهایی تأیید نشده؛ پارسر پیش‌فرض در `excel/id_parse.py` است.
