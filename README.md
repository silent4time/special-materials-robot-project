# بازوی گزارش مواد / تاندیش (بله)

ربات پیام‌رسان **بله** برای دریافت **سه فایل Excel مشخص**، اعمال کنترل دسترسی نقش‌محور (RBAC)، **تحلیل مصرف مواد تاندیش**، و تولید **گزارش PDF ترکیبی**. رابط کاربری فارسی است.

📘 **راهنمای کاربری کامل (PDF، فارسی):** [docs/nasoz_guide.pdf](docs/nasoz_guide.pdf) — منابع ساخت آن در [docs/guide_src/](docs/guide_src/).

## استانداردهای کارخانه برای نوع تاندیش

این سامانه دقیقاً سه نوع تاندیش را به‌عنوان استاندارد کارخانه می‌پذیرد (برای «موجودی روزانه سایت» و مصرف ماهانه):

- `slab` — **تاندیش اسلب**
- `bloom` — **تاندیش بلوم**
- `billet` — **تاندیش بیلت**

در Excel می‌توان کلید انگلیسی یا برچسب فارسی را وارد کرد؛ هنگام بارگذاری هر سه به برچسب فارسی استاندارد تبدیل می‌شوند.

## اهداف محصول

1. **تشخیص مقدار مواد مصرفی روزانه** — میانگین مصرف روزانه هر ماده / تاندیش از فایل موجودی روزانه سایت (و در صورت نبود، تقریب از مصرف ماهانه ÷ ۳۰).
2. **پیشنهاد درخواست مواد توسط ربات** —  
   `suggest_qty = max(0, forecast_need − remaining_inventory)`
3. **گزارش مقدار مواد مصرفی بر حسب زمان درخواستی** — امروز / ۷ روز / ۳۰ روز یا  
   `از YYYY-MM-DD تا YYYY-MM-DD`
4. **مواد بحرانی** — `days_of_cover = remaining / avg_daily < CRITICAL_DAYS` (پیش‌فرض ۳).
5. **پیش‌بینی نیاز** — `forecast_need = avg_daily × requested_days`
6. **گزارش مواد مازاد** — موجودی خیلی بیش از نیاز کوتاه‌مدت (جزئیات پایین).

## نصب روی سرور

روی Ubuntu 22.04/24.04 یا Debian 12، در یک ترمینال SSH (PuTTY یا CMD/PowerShell با `ssh`) با root یا sudo. دو روش وجود دارد؛ جزئیات کامل در **[DEPLOY.md](DEPLOY.md)**.

### روش الف — نصب آنلاین با یک دستور (سرور به GitHub و PyPI دسترسی دارد)

1. با PuTTY یا `ssh root@IP-سرور` وارد سرور شوید.
2. اجرا کنید:
   ```bash
   cd /root
   bash <(curl -fsSL https://raw.githubusercontent.com/silent4time/special-materials-robot-project/main/install.sh)
   ```
   (`curl -fsSL https://raw.githubusercontent.com/silent4time/special-materials-robot-project/main/install.sh | bash` هم کار می کند.)
3. لوگو و **منوی اصلی** نمایش داده می شود؛ **1** (نصب جدید) را بزنید و به ویزارد فارسی پاسخ دهید: توکن (با بررسی `getMe`)، نام کاربری ربات، شناسه مالک (اختیاری)، پورت/آدرس و ورود پنل وب. سپس بسته ها (tesseract فارسی و ...)، venv، دیتابیس و دو سرویس systemd (`nasoz-bot`، `nasoz-web`) نصب و تست سلامت می شود. ریپو در `/root/special-materials-robot-project` قرار می گیرد.
4. به روزرسانی بعدی:
   ```bash
   cd /root/special-materials-robot-project
   bash install.sh --update        # فقط برنامه (پشتیبان DB + git pull + pip + migrate + ری استارت)
   bash install.sh --full-update   # اول ارتقای سیستم عامل، بعد برنامه
   ```

### روش ب — نصب آفلاین با بسته (سرور به GitHub/PyPI نمی رسد، مثلا داخل ایران)

1. فایل بسته `nasoz_offline_<تاریخ>_<commit>.tar.gz` را دانلود کنید (ساخت روی سیستمی با اینترنت آزاد: `bash scripts/build_offline_bundle.sh`). اگر بیشتر از 25 مگابایت باشد ممکن است تکه تکه برسد: `.part0`، `.part1`، `.part2` — همه را دانلود کنید.
2. با **WinSCP** (SFTP، کاربر root) فایل (یا همه تکه ها) را به پوشه `/root` سرور بفرستید.
3. در SSH، اگر تکه تکه بود، یکی کنید:
   ```bash
   cd /root
   cat nasoz_offline_X.tar.gz.part0 nasoz_offline_X.tar.gz.part1 nasoz_offline_X.tar.gz.part2 > nasoz_offline_X.tar.gz
   ```
4. سالم بودن فایل را بررسی کنید؛ عدد باید با sha256 اعلام شده یکی باشد:
   ```bash
   sha256sum nasoz_offline_X.tar.gz
   ```
5. باز کنید و نصب کنید (نصب در `/opt/nasoz`):
   ```bash
   tar -xzf nasoz_offline_X.tar.gz
   cd nasoz_offline_X
   bash install_offline.sh      # منوی اصلی ← 1 (نصب جدید)؛ بدون منو: --install
   ```
6. به روزرسانی با بسته جدید (`.env` و `data/` حفظ می شود):
   ```bash
   cd /root && tar -xzf nasoz_offline_<جدید>.tar.gz && cd nasoz_offline_<جدید>
   bash install_offline.sh --update
   # یا: bash /opt/nasoz/scripts/install.sh --update --offline /root/nasoz_offline_<جدید>.tar.gz
   ```

### منوی اصلی
اجرای `bash install.sh` (یا دستور curl بالا، یا `bash install_offline.sh`) **بدون پرچم** در ترمینال، لوگو و این منو را نشان می دهد:
`1) نصب جدید  2) به روزرسانی  3) وضعیت  4) گرفتن بک آپ  5) بازیابی بک آپ  6) تعمیر  7) مدیریت سرویس ها  8) مشاهده لاگ ها  9) تغییر تنظیمات (.env)  10) نصب دستیار هوشمند (اختیاری)  0) خروج`.
«وضعیت» نسخه، سرویس ها، اتصال به بله/GitHub/PyPI/mirror، حجم داده و آخرین بک آپ را نشان می دهد (توکن هرگز چاپ نمی شود). همه پرچم ها مثل قبل بدون منو کار می کنند؛ جزئیات در DEPLOY.md «منوی اصلی نصب کننده».

### بازگردانی بک آپ روی سرور
فایل ZIP بک آپ را با WinSCP به `/root` بفرستید و در پوشه نصب اجرا کنید:
```bash
cd /opt/nasoz          # روش آنلاین: cd /root/special-materials-robot-project
bash scripts/install.sh --restore /root/nasoz_backup_1405-07-25_0200.zip
```

### بعد از نصب (هر دو روش)
1. پورت پنل وب را باز کنید: `sudo ufw allow 8000/tcp` و در فایروال/پنل ابری ارائه دهنده سرور هم پورت 8000/TCP را باز کنید.
2. در بله به ربات `/start` بفرستید — **اولین کسی که /start بزند مالک می شود**.
3. پنل وب: `http://IP-سرور:8000/login` (اگر ورود وب هنوز فعال نیست: `bash install.sh --web-login` در پوشه نصب).
4. **فقط یک نمونه از ربات با هر توکن** روشن باشد؛ نسخه های دیگر را خاموش کنید.

| دستور (در پوشه نصب) | کار |
|------|-----|
| `bash install.sh --update` | به روزرسانی برنامه: پشتیبان DB ← `git pull` ← `pip install -r requirements.txt` ← migrate ← restart ← تست سلامت (`.env` و `data/` حفظ می شود) |
| `bash install.sh --system-upgrade` | `apt-get update && apt-get upgrade -y` غیرتعاملی (`DEBIAN_FRONTEND=noninteractive`، فایل های پیکربندی موجود حفظ می شود) + restart |
| `bash install.sh --full-update` | هر دو (اول سیستم، بعد برنامه) |
| `bash install.sh --update --offline BUNDLE.tar.gz` | به روزرسانی از بسته آفلاین (بدون GitHub/PyPI) |
| `bash install.sh --repair` | خودترمیم بسته ها/venv |
| `bash install.sh --restore FILE.zip` | بازگردانی بک آپ روی سرور: بررسی manifest/sha256 ← توقف سرویس ها ← بک آپ «پیش از بازگردانی» ← بازگردانی ← migrate ← استارت ← تست سلامت |
| `... --dry-run` | فقط چاپ دستورها، بدون تغییر |

نصب کننده برای هر مرحله نوار پیشرفت (`[n/کل] ٪ ███░░`) نشان می دهد و خروجی کامل را در `data/logs/nasoz_install_<تاریخ>.log` نگه می دارد؛ در خطا مرحله و مسیر لاگ گفته می شود. پیام های فارسی ترمینال بدون نیم فاصله چاپ می شوند تا در PuTTY/CMD کلمه ها به هم نچسبند.

**دستیار هوشمند صوتی (`--with-assistant`، اختیاری):** بدون نیاز به ollama.com (که آی پی ایران را با 403 رد می کند) نصب می شود: باینری Ollama از GitHub releases، مدل `qwen2.5:3b` از hf-mirror.com یا huggingface.co، و Whisper/Piper از PyPI. روی سرور نصب شده: `cd /opt/nasoz && sudo bash install.sh --with-assistant` (یا گزینه 10 منو؛ مدل دیگر: `--model qwen2.5:1.5b`، همچنین `--whisper base`، `--no-piper`، `--no-whisper`)؛ بدون اینترنت آزاد: بسته `bash scripts/build_assistant_bundle.sh` و `sudo bash install.sh --assistant-offline FILE.tar`. هر خطا فقط هشدار است و ربات بدون دستیار کار می کند. جزئیات: DEPLOY.md، بخش «دستیار هوشمند صوتی».

### 💾 بک‌آپ و بازگردانی
- **بک‌آپ کامل** = ZIP با نام تاریخ شمسی (مثل `nasoz_backup_1405-07-25_0200.zip`؛ دستی `…_manual.zip`، پیش از بازگردانی `…_pre-restore.zip`) شامل کپی سازگار پایگاه داده (sqlite backup API)، `uploads/` (فایل‌های منبع اصلی و …)، `data/bot_assets/`، تنظیمات `.env` **بدون** توکن/رمز/کلیدها، و `manifest.json` (commit، تاریخ، شمارش‌ها، sha256 هر فایل). محل: `data/backups/` روی سرور.
- **دستی:** ربات «⚙️ تنظیمات ← 💾 بک‌آپ» (فایل به‌صورت سند فرستاده می‌شود؛ بالای ۵۰ مگابایت ← دانلود از وب) و وب `/settings/backups`. مجوز «بک‌آپ» (پیش‌فرض مالک/مدیر، قابل تغییر در «🔐 دسترسی نقش‌ها»).
- **خودکار:** هر شب ۰۲:۰۰ به وقت تهران داخل فرآیند ربات (اگر ربات آن ساعت خاموش بود، پس از روشن‌شدن همان روز انجام می‌شود؛ خطا ← پیام به مالک و تلاش دوباره پس از ۳۰ دقیقه)؛ یک نسخه برای مالک در بله فرستاده می‌شود.
- **نگهداری:** ۷ بک‌آپ روزانهٔ آخر + آخرین بک‌آپ ۴ هفتهٔ اخیر؛ بک‌آپ‌های دستی و پیش از بازگردانی تا ۳۰ روز هرگز خودکار حذف نمی‌شوند.
- **بازگردانی (فقط مالک):** ربات (ارسال ZIP ← بررسی ← خلاصه ← دو تأیید)، وب (بارگذاری ← خلاصه ← تیک + تایپ «بازگردانی»)، سرور `bash install.sh --restore`. همیشه اول یک بک‌آپ خودکار گرفته می‌شود؛ ZIP نامعتبر/بیگانه یا مسیر ناامن رد می‌شود.

## گزارش هدف اصلی

منو: **گزارش‌ها / تحلیل تاندیش** → **🎯 گزارش هدف اصلی** (مالک / مدیر / کاردان مسئول). وب: `/reports/main-goal`.

### الف) ثبت ورودی در DB
- **📸 عکس آمار تولید** — فقط تب «ریخته گری» صفحه otsteel.ksc.ir/productionstatistics. سرویس مشترک `services/main_goal_production_ocr.py` تب را تشخیص می‌دهد (`detect_report_tab`): عکس تب «کوره» (سرستون «شماره کوره»، «تعداد به اسلب»، «تعداد به بلوم بیلت»، نمودار «به تفکیک کوره ها») یا تب نامشخص در ربات و وب **رد** می‌شود، چیزی ذخیره نمی‌شود و هشدار فارسی نمایش داده می‌شود. تب ریخته‌گری: ردیف/ستون CCM → تناژ بخش (اسلب=CCM1+2، بلوم=CCM3، بیلت=CCM4+5) و تعداد ذوب هر بخش در `main_goal_production` (`ccm*_tons`، `slab/bloom/billet_melt_count`). ⚠ چیدمان واقعی تب ریخته‌گری هنوز دیده نشده؛ ردیف‌ها با `source_status='casting_needs_validation'` ذخیره می‌شوند تا با عکس واقعی اعتبارسنجی شود. نشانه‌های قطعی تب ریخته‌گری (از عکس‌های واقعی ۱۴۰۵/۰۷/۱۴): نمودار «وزن محصول به تفکیک ریخته گری (ماهیانه/سالیانه)»، ردیف‌های «مجموع اسلب ها» و «مجموع بلوم بیلت ها» و سرستون «شماره CCM» — ردیف «مجموع بلوم بیلت ها» دیگر نشانهٔ تب کوره حساب نمی‌شود. تاریخ سربرگ صفحه («سه شنبه ۱۴ مهر ۱۴۰۵» = امروز) هرگز ماه گزارش در نظر گرفته نمی‌شود. اگر ارقام عکس گوشیِ مانیتور خوانا نباشد، تب پذیرفته می‌شود ولی چیزی ذخیره نمی‌شود و اصلاح دستی خواسته می‌شود.
- ردیف‌های قدیمی تب کوره (بذر تیر/مرداد/شهریور ۱۴۰۵) حذف نشده‌اند: مهاجرت DB آن‌ها را `source_status='furnace_tab_provisional'` علامت می‌زند، از محاسبات تناژ بخش‌ها حذف می‌شوند و در UI با «نیاز به عکس تب ریخته‌گری» نمایش داده می‌شوند؛ با ثبت عکس تب ریخته‌گری همان ماه جایگزین می‌شوند.
- **📤 گزارش جامع تاندیش در سکوئنس** (فایل تجمیعی تعداد تاندیش و ذوب سه بخش): ردیف‌ها در `main_goal_tundish_sequences`؛ تجمیع ماهانه (تعداد سکوئنس=تاندیش، جمع ذوب، تعویض شرود/نازل) در `main_goal_consumption`. ردیف‌ها بر اساس **ماه شروع ریخته‌گری × بخش ماشین** (اسلب ۱/۲، بلوم، بیلت ۱/۲) تفکیک و هر جفت (ماه، بخش) جداگانه جایگزین می‌شود؛ پس یک لاگ چندماهه/چندبخشی درست ثبت می‌شود. بخش انتخابی کاربر فقط برای فایل تک‌بخشی اعمال می‌شود. سکوئنسی که در آخرین روز ماهِ اولِ فایل شروع و در ماه بعد تمام شده (لبهٔ فایل) به ماه بعد منظور می‌شود تا ماه تک‌ردیفی ساخته نشود.
- اصلاح دستی تولید در ربات/وب اگر OCR فیلدی را از دست بدهد.
- آپلود ۴ فایل Excel یک‌جا (قدیمی) همچنان نرمال‌سازی می‌کند.

### ب) درخواست گزارش از سابقه

### استخراج شناسه (`id`) و خروجی تمیز

**فرض پیش‌فرض** (قابل تنظیم در `excel/id_parse.py` تا وقتی کاربر فرمت نهایی را تأیید کند):

> از ابتدای «کد و شرح کالا»، اولین توکن شامل رقم (و حروف اختیاری) را قبل از اولین فاصله، خط تیره فاصله‌دار ` - `، یا خط تیره en `–` بردار.

نمونه‌ها:

- `ACID01 - اسید سولفوریک` → `id=ACID01` ، `product_name=اسید سولفوریک`
- `55 ماده` → `id=55` ، `product_name=ماده`

خروجی تمیز (`product_inventory`) ستون‌های زیر را دارد (بدون متن ترکیبی خام):

`category_code`, `id`, `product_name`, `keyword`, `quantity`, `priority`

`product_name` برای اتصال به نام ماده در مصرف روزانه/ماهانه استفاده می‌شود.

### فیلتر و اولویت

1. فقط ردیف‌هایی که `category_code` در جدول `category_codes` (لیست مجاز) باشد نگه داشته می‌شوند.
   کد **۱۸۰۰** مخصوص **اقلام مازاد** است و در لیست پیش‌فرض (`DEFAULT_CATEGORY_CODES`) همیشه هست تا هنگام آپلود منبع اصلی حذف نشود.
2. ستون `اولویت` / `priority`؛ خانه خالی = **۱** (بالاترین). `priority == 0` یعنی «بدون اولویت»: ردیف ذخیره می‌شود ولی در پیشنهاد درخواست مواد / درخواست مواد استفاده نمی‌شود.
   ستون «سطح ریخته گری» (`casting_floor`) جای «سایر نواحی» (`other_areas`) را گرفته؛ فایل‌های قدیمی خودکار منتقل می‌شوند.
   فقط شیت «ریز اطلاعات» نگه داشته می‌شود (Sheet1 / کل موجودی / Sheet3 از فایل ذخیره‌شده حذف می‌شوند).
   پیمانکار/شرکت: در شناسه مواد پیمانکار، چهار رقم دوم از چپ `0000` است (`excel/id_parse.py`) — این قاعده مرجع است و ستون فایل را بازنویسی می‌کند.
3. شناسه نامعتبر / موجودی غیرعددی حذف می‌شود.
4. نسخه تمیز در `uploads/<user>/<session>/cleaned/product_inventory.xlsx` و رکورد در `extracted_datasets` ذخیره می‌شود.
5. اگر لیست مجاز خالی باشد، ربات می‌گوید ابتدا از منو کد دسته اضافه کنید.

## منبع اصلی = فایل مرجع کاربر (قاعده ۱۴۰۵/۰۷/۱۴)

- آپلود موجودی/انبار («📥 موجودی انبار»، مواد مصرفی، فایل مصرف ماهانه‌ای که قالب منبع اصلی دارد) فقط ردیف‌های موجود را به‌روز می‌کند و ردیف با **شناسه جدید** را فقط وقتی اضافه می‌کند که کد ۴ رقمی آن در منبع اصلی باشد؛ بقیه اضافه نمی‌شوند و در پیام آپلود فهرست می‌شوند (`services.main_source.filter_inventory_upload` / `skipped_rows_note_fa`، مشترک ربات و وب).
- کد ۴ رقمی جدید فقط با «افزودن رکورد» (تنظیمات) یا آپلود فایل کامل منبع اصلی توسط کاربر مجاز («📥 ورود فایل اکسل منبع اصلی» در ربات، صفحه تنظیمات منبع اصلی در وب؛ مالک/مدیر/کاردان مسئول).
- **کد ۱۸۰۰ (مازاد):** ردیف جدید ۱۸۰۰ از آپلود موجودی/انبار هرگز اضافه نمی‌شود (رد و با ⛔ فهرست می‌شود)؛ فقط «افزودن رکورد» یا آپلود فایل کامل منبع اصلی توسط کاربر مجاز (مالک/مدیر/کاردان مسئول) ردیف جدید ۱۸۰۰ اضافه می‌کند. به‌روزرسانی موجودی ردیف‌های ۱۸۰۰ موجود همیشه مجاز است. کد ۱۸۰۰ همچنان از اقلام بحرانی/پیش‌بینی مستثنی است و در گزارش مازاد می‌آید.
- اولین بارگذاری (وقتی منبع اصلی هنوز وجود ندارد) فیلتر نمی‌شود.
- حذف رکورد: `services.main_source.delete_row` (+ ثبت فعالیت `delete_main_source_record`).

## گزارش اقلام بحرانی (تفکیک شرکت / پیمانکار)

- منطق مشترک ربات و وب: `analytics/critical_items.py` + `services/critical_items_report.py` (بدون کپی منطق).
- **تعریف «نیاز» (از ۱۴۰۵/۰۷/۱۴):** **تاریخ گزارش = امروز** (شمسی، در عنوان/سربرگ/نام فایل؛ انتخاب ماه حذف شد). «میانگین مصرف ماهانه بر اساس ۳ ماه گذشته» = نرخ‌های هر کد × **میانگین** تعداد تاندیش **۳ ماه کامل قبل از تاریخ گزارش** (`services.critical_items_report.critical_basis`): برای هر ماه **لاگ توالی تاندیش** (`main_goal_tundish_sequences`؛ هر سکوئنس = یک بار استفاده از تاندیش؛ بخشی که در آن ماه سکوئنس ندارد = ۰) مقدم است؛ فقط ماهی که لاگ ندارد از «ثبت تعداد تاندیش ماهانه» (دستی) پر می‌شود، مگر آن ثبت با `exclude_from_basis` علامت خورده باشد (مثل نمونه شهریور ۱۴۰۵ بیلت ۷۰/اسلب ۱۰۰ — برای ممیزی می‌ماند؛ ثبت دوباره آن ماه علامت را برمی‌دارد). ماه بدون هیچ داده کنار می‌رود و در سربرگ ذکر می‌شود. لاگ توالی ستون نوسازی/پچینگ ندارد: «با نوسازی» = هر تاندیش نوسازی + پچینگ، «بدون نوسازی» = فقط پچینگ. «نیاز» به بالا گرد می‌شود. **افق** از ستون «سازنده»: وارداتی ۶ ماه، داخلی ۳ ماه؛ خالی/نامشخص → داخلی (۳ ماه) و در «توضیحات» فهرست می‌شود؛ کدِ دارای ردیف داخلی و وارداتی (مختلط) → ۶ ماه. «مصرف پیش‌بینی‌شده در افق» = میانگین ماهانه × افق؛ **«نیاز» = max(0, مصرف پیش‌بینی‌شده − موجودی)** و فقط اقلامی با نیاز مثبت فهرست می‌شوند (مرتب بر اساس حد تحمل). **ستون‌های خروجی (از ۱۴۰۵/۰۷/۲۵) فقط ستون‌های قالب کاربر:** ردیف | کد چهاررقمی | کد و شرح کالا | موجودی | واحد | نیاز | حد تحمل(روز) (ردیف/کد به تصمیم کاربر جابه‌جا نسبت به قالب) (= موجودی ÷ مصرف روزانه، ماه ۳۰ روزه)؛ میانگین ماهانه، افق، مبدأ و مصرف پیش‌بینی‌شده فقط داخل محاسبه‌اند (پیام ربات و دستیار هنوز مبدأ نامشخص/مختلط را می‌گویند). بلوک «توضیحات» زیر جدول تقریباً خالی است: فقط «افق محاسبه: اجناس داخلی ۳ ماه، اجناس وارداتی ۶ ماه.» و یک سطر «تاریخ گزارش … — مبنا: مصرف هر تاندیش (منبع اصلی) × میانگین ماهانهٔ تعداد تاندیش …» + سطرهای خالی حاشیه‌دار و توضیحات کاربر.
- برچسب ستون `contractor_or_company` در همهٔ خروجی‌ها و فرم‌ها **«تأمین‌کننده»** است (مقادیر همان «شرکت»/«پیمانکار»)؛ واردکننده هر دو عنوان «تأمین‌کننده» و «پیمانکار / شرکت» (و گونه‌ها) را می‌پذیرد.
- **قاعده شناسه (مرجع، از ۱۴۰۵/۰۷/۱۴):** پیمانکار/شرکت از روی **شناسه مواد** تعیین می‌شود: اگر رقم‌های ۵ تا ۸ «0000» باشد (مثل `3787 0000 9032J`) → «پیمانکار»، وگرنه «شرکت» (`excel/id_parse.py` → `apply_id_segment_rule`). واردکنندهٔ منبع اصلی (ربات و وب)، هر ذخیرهٔ منبع اصلی (ویرایش/افزودن رکورد) و تفکیک تحلیل‌ها (`classify_contractor_or_company`) همین قاعده را اعمال می‌کنند؛ ستون «تأمین‌کننده» (نام قبلی: «پیمانکار / شرکت»؛ هر دو عنوان در ورود پذیرفته می‌شود) فایل فقط وقتی شناسه کوتاه/ناقص است استفاده می‌شود و اگر با قاعده مغایر باشد در پیام آپلود هشدار و فهرست ردیف‌ها نمایش داده می‌شود. «شرکت» → گزارش اصلی، «پیمانکار» → گزارش جداگانه. موجودی، نرخ و نقطه بحرانی هر بخش فقط از ردیف‌های همان بخش است.
- **کد ۱۸۰۰ = همیشه مازاد:** ردیف‌های کد دسته ۱۸۰۰ هرگز قلم مصرفی نیستند — از اقلام بحرانی (`drop_surplus_rows`) و از تطبیق کالا/موجودی هدف اصلی و پیش‌بینی (`section_inventory`) کنار گذاشته می‌شوند، حتی اگر اولویت یا نرخ داشته باشند؛ فقط در گزارش مازاد می‌آیند.
- تجمیع بر اساس کد ۴ رقمی (در هر بخش شرکت/پیمانکار جداگانه): ردیف‌های با اولویت ۰ (= استفاده نمی‌شود) کنار گذاشته می‌شوند؛ موجودی = جمع موجودی **همه** ردیف‌های باقیماندهٔ آن کد (حتی ردیف‌هایی که نرخ مصرف ندارند و حتی موجودی زیر ۱۰۰ یا صفر). نرخ‌های نوسازی/پچینگ/سطح ریخته‌گری و نقطه بحرانی **مقدار واحدِ هر کد** هستند = بیشینه همین ردیف‌ها (یک بار، نه جمع ردیف‌ها). کد وقتی فهرست می‌شود که نیاز (مصرف پیش‌بینی‌شده در افق − موجودی) در حالت انتخابی مثبت باشد. هیچ حد «زیر ۱۰۰» وجود ندارد. هشدار نقطه بحرانی وقتی جمع موجودی ≤ آن.
- **خانه‌های ادغام‌شده (Merge) در «ریز اطلاعات»:** ورود اطلاعات مشترک (`excel.processor.fill_merged_cells`، ربات و وب) هر محدوده ادغام را باز می‌کند و مقدار را در همه ردیف‌های زیر آن کپی می‌کند (نرخ‌ها، نقطه بحرانی، واحد، اولویت، پیمانکار/شرکت، …)؛ فقط **موجودی** (مقدار هر ردیف) کپی نمی‌شود: روی ردیف اول می‌ماند و بقیه ۰ می‌گیرند. فایل کاربر تغییر نمی‌کند. ادغامی که دو بخش شرکت/پیمانکار را می‌پوشاند در هر ردیف کپی می‌شود و هر بخش نرخ خودش را دارد.
- **نیاز مشترک گروه:** ادغامی که روی چند کد ۴ رقمی است (مثل نرخ ۶ نازل‌های بیلت 1710/1712/1714/1716/1717/1718) در ستون `rate_group` («گروه نرخ مشترک (ادغام)») ثبت می‌شود. پیش‌فرض `config.CRITICAL_SHARED_MERGE_MODE = "pooled"`: یک ردیف گروه (کدها با «/»، پررنگ) = جمع موجودی کدها در برابر مصرف مشترک در افق (نرخ یک بار × میانگین تعداد تاندیش × افق)، حد تحمل و وضعیت بحرانی از همین ردیف؛ زیر آن هر کد با موجودی خودش و «نیاز مشترک گروه». در شمارش اقلام، گروه یک قلم است. با `"per_code"` هر کد نرخ کامل را جداگانه می‌گیرد.
- **تخصیص بخش (بیلت/بلوم/اسلب) — `analytics/section_rules.py`، مشترک بین اقلام بحرانی و هدف اصلی/پیش‌بینی:** برای کدی که هم ردیف «شرکت» و هم «پیمانکار» با اولویت غیر صفر دارد (مثل 1637): مصرف **بیلت** فقط از ردیف‌های شرکت، مصرف **بلوم** فقط از ردیف‌های پیمانکار، و مصرف **اسلب** از ردیف‌های پیمانکار و ردیف‌های شرکت با محل استفاده «اسلب» (اولویت ≠ ۰) حساب می‌شود — حتی اگر خانه ادغام‌شده نرخ بخش دیگر را به آن ردیف کپی کرده باشد. سطح ریخته‌گری دست نمی‌خورد. در هدف اصلی/پیش‌بینی تطبیق کالا و موجودی هر بخش فقط روی ردیف‌های مجاز همان بخش انجام می‌شود.
- حالت محاسبه (قبل از تولید انتخاب می‌شود): «با نوسازی» = تعداد تاندیش × (نرخ نوسازی + پچینگ) + سطح ریخته‌گری × مجموع تاندیش‌ها (رفتار قبلی، پیش‌فرض)؛ «بدون نوسازی» = تعداد تاندیش × فقط نرخ پچینگ + همان سطح ریخته‌گری. ستون‌های نوسازی و پچینگ بیلت/بلوم/اسلب در منبع اصلی جدا ذخیره‌اند؛ اقلامی که فقط نرخ نوسازی دارند در حالت «بدون نوسازی» نیاز صفر دارند و فهرست نمی‌شوند. سطح ریخته‌گری به نوسازی تاندیش وابسته نیست و در هر دو حالت منظور می‌شود. حالت در عنوان/زیرعنوان PDF، سربرگ شیت‌ها و «توضیحات» اکسل، نام فایل و پیام ربات می‌آید.
- ربات: «📄 تولید گزارش اقلام بحرانی» → دکمه‌های شیشه‌ای «با نوسازی» / «بدون نوسازی» (نوشتن همین عبارت هم پذیرفته است). وب: رادیو «حالت محاسبه نیاز» روی کارت اقلام بحرانی.
- **گردش کار پیش‌نویس → توضیحات → تأیید → بایگانی (ربات و وب، مشترک: `services/critical_report_archive.py`، جدول `critical_item_reports`):** تولید گزارش یک **پیش‌نویس** می‌سازد (PDF شرکت، PDF پیمانکار، اکسل دو شیتی؛ نام فایل `لیست_اقلام_بحرانی_<تاریخ>_<حالت>_پیش‌نویس_<شماره>`). کاربر می‌تواند توضیحات خودش را بنویسد/ویرایش/حذف کند (هر خط یک سطر بلوک «توضیحات»؛ حداکثر ۱۲ سطر / ۲۰۰۰ نویسه) یا بدون توضیحات تأیید کند؛ «تأیید» نسخهٔ نهایی (`…_تأییدشده_<شماره>`) را در `UPLOAD_DIR/critical_reports/<شماره>/final/` (داخل پشتیبان، بدون پاک‌سازی ۶۰ روزه) ذخیره می‌کند و گزارش دیگر ویرایش نمی‌شود. ردیف‌ها در زمان پیش‌نویس ثابت می‌شوند؛ اگر فایلی گم شود از همان ردیف‌های ذخیره‌شده دوباره ساخته می‌شود. فهرست تأییدشده‌ها: ربات «🗂 گزارش‌های تأییدشده اقلام بحرانی» (پیش‌نویس‌های باز هم برای ادامه) و وب کارت اقلام بحرانی. پیش‌نویس ربات در وب قابل تأیید است و برعکس. دسترسی: `report.critical`.
- وب: `POST /reports/critical-items/draft` (renovation) → `GET /reports/critical-items/report/<id>` (پیش‌نمایش، کادر توضیحات، دکمه‌های ذخیره/تأیید/حذف توضیحات/لغو) → `POST …/<id>/notes` (action=save|approve|clear|cancel؛ «تأیید» متن کادر را اول ذخیره می‌کند) و دریافت `GET …/<id>/file/xlsx|company|contractor`. نشانی‌های قدیمی `/reports/critical-items?segment=…` و `/reports/critical-items.xlsx` هنوز خروجی مستقیم (بدون بایگانی) می‌دهند.
- دفتر تعدیل موجودی (`inventory_ledger`) فقط یک بار و داخل `load_primary_inventory` اعمال می‌شود؛ روی خروجی آن دوباره اعمال نکنید.
- همه PDFها (ربات و وب) A4 عمودی‌اند؛ جدول‌ها با عرض ستون خودکار، شکستن خط راست‌به‌چپ و تکرار سطر عنوان در صفحات بعد.
- تست: `python scripts/smoke_critical_split_portrait.py` (PNG صفحه اول هر نوع گزارش در `reports/smoke_portrait/`).

### مصرف هر تاندیش و ترکیب چند بخش (۷۰ بیلت + ۲۰ بلوم + ۱۰۰ اسلب)
- نرخ‌های منبع اصلی (نوسازی/پچینگ بیلت، بلوم، اسلب + سطح ریخته‌گری) **مصرف یک تاندیش** هر نوع‌اند و در اقلام بحرانی (× میانگین ماهانهٔ تعداد تاندیش) و «🧮 نیاز مواد برای N تاندیش» مشترک‌اند.
- ترکیب: ربات در مرحلهٔ بخش یا تعداد «بیلت ۷۰ بلوم ۲۰ اسلب ۱۰۰» (یا «۷۰ بیلت، ۲۰ بلوم و ۱۰۰ اسلب») را می‌پذیرد (`n_tundish_report.parse_mix`)؛ وب `GET /reports/n-tundish-mix(.xlsx)?billet=&bloom=&slab=&renovation=`. نیاز کل = Σ (مصرف هر تاندیش نوع × تعداد) + سطح ریخته‌گری × کل تاندیش‌ها؛ کسری = نیاز − موجودی. ستون‌های پایهٔ مواد + ستون مصرف هر تاندیش هر نوع.
- `services/per_tundish_rates.py` (فقط برای مقایسه، `generate_mix_files(..., empirical=True)`): حوالهٔ انبار هر تاندیش از استخراج مصرف ماهیانه (دستور کار ← بخش) ÷ تعداد تاندیش لاگ توالی همان ماه‌ها؛ چون حواله ≠ مصرف واقعی و نمونهٔ بلوم کوچک است، در محاسبهٔ نیاز به کار نمی‌رود.

## نقش‌ها (RBAC)

| نقش | دسترسی |
|-----|--------|
| مالک / مدیر | همه ردیف‌ها + مدیریت کاربران + تنظیمات اقلام |
| کاردان مسئول | همه ردیف‌ها (مثل مالک/مدیر برای فیلتر داده) + تنظیمات اقلام سایت؛ هویت = شناسه بله |
| تکنسین | فقط ورود تعاملی «موجودی روزانه سایت» (سه گروه)؛ بدون تنظیمات/گزارش؛ فیلتر assignee در صورت وجود ستون |
| 👷 مسئول شیفت (`shift_supervisor`) | پیش‌فرض مثل تکنسین: «گزارش تاندیش بعد از ریخته‌گری» + «موجودی روزانه سایت» |

جدول بالا **پیش‌فرض** است. مالک/مدیر از «⚙️ تنظیمات ← 🔐 دسترسی نقش‌ها» (ربات، چک‌باکس inline) یا
`/settings/permissions` (وب) هر بخش را برای هر نقش روشن/خاموش می‌کنند (جدول `role_permissions`؛
اعمال در هر دو فرایند ظرف ~۲ ثانیه). مالک قفل است؛ «کاربران» و «دسترسی نقش‌ها» همیشه فقط مالک/مدیر.
همهٔ منوها، handlerها و routeهای وب از `services/permissions.py` می‌پرسند. هر تغییر در فعالیت کاربران ثبت می‌شود.

**منبع اصلی یکتا (کل کارخانه):** همیشه آخرین استخراج هر کاربری که آپلود/ویرایش کرده؛ ویرایش مالک/مدیر/کاردان
مسئول فوراً برای همه اعمال می‌شود (دیگر نسخهٔ جدا برای هر کاربر وجود ندارد).

شناسایی افراد با `bale_user_id` است. هر ورودی داده ثبت‌کننده را ذخیره می‌کند (`bale_user_id` / `created_by` / `assigned_by`). ستون `scope` برای سازگاری قدیمی نگه داشته شده و برای کاردان مسئول الزامی نیست.

**منبع اصلی** ستون domain/assignee ندارد → برای همه کاربران مجاز **قابل مشاهدهٔ کامل** است (plant-wide). موجودی روزانه سایت دیگر Excel تکنسین نیست.

### موجودی روزانه سایت (ورود تعاملی)

مسیر اصلی تکنسین/کاربران: منو → سه گروه → ورود مقدار یکی‌یکی. داده در SQLite ذخیره می‌شود.

| جدول | نقش |
|------|-----|
| `catalog_items` | فهرست اصلی اقلام (`id`, `name_desc`, `category_code`, `active`) — از استخراج منبع اصلی seed می‌شود |
| `catalog_group_assignments` | تخصیص یک گروه به هر قلم: `slab` / `bloom` / `billet` |
| `site_stock_entries` | موجودی روزانه؛ upsert یکتا بر `(entry_date, tundish_group, item_id)`؛ فیلدهای `quantity` + `pallet_qty`/`unit_qty`/`quantity_detail` برای توسعه بعدی |

برچسب‌های منو: **موجودی مواد اسلب** / **موجودی مواد بلوم** / **موجودی مواد بیلت**.

**فهرست‌های ورودی (قاعده ۱۴۰۵/۰۷/۱۸):** هر سه فهرست به‌صورت پویا از منبع اصلی زنده ساخته می‌شوند (`services/site_stock_lists.py`، مشترک ربات و وب `/stock`):
- یک سطر به‌ازای هر (کد ۴ رقمی، **کلید واژه**) در هر بخش؛ نام نمایش = ستون «کلید واژه» (سلول ادغامی داخل همان کد پر می‌شود؛ اگر خالی بود «شرح کالا»). نازل‌های 1710…1718 هر کد یک سطر (نازل 16.5 … نازل 19) در بلوم و بیلت.
- فقط اولویت ≠ ۰؛ کد ۱۸۰۰ (مازاد) هرگز.
- **شرود هرگز در فهرست موجودی روزانه نیست** (کد 1581 و هر قلمی که کلید واژه/شرح آن «شرود»/shroud دارد) — اینجا درخواست لازم ندارد. بقیه ردیف‌های «سطح ریخته گری …» (مثل بتن 80 گان 1451 → بیلت، بتن پلی 60 1658 → اسلب و بلوم) در فهرست همان بخش می‌مانند؛ فهرست جدای سطح ریخته‌گری وجود ندارد (تصمیم کاربر ۱۴۰۵/۰۷/۱۸). CHECK جدول‌ها هنوز کلیدهای قدیمی `cast_*` را می‌پذیرد تا داده قدیمی (در صورت وجود) خوانا بماند.
- بخش از «محل استفاده» (بیلت/بلوم/اسلب؛ «بلوم / بیلت» → هر دو؛ بدون واژه بخش → ستون‌های نرخ همان بخش) + قاعده مشترک شرکت/پیمانکار `analytics.section_rules` برای کدهای دوطرفه (بیلت = شرکت، بلوم = پیمانکار، اسلب = پیمانکار + شرکتِ دارای «اسلب»).
- سطرها با شناسه مصنوعی `SS:<بخش>:<کد>:<hash>` و `assigned_by=system:main_source_keyword` در کاتالوگ نگه داشته می‌شوند (خارج از فهرست درخواست مواد/کاتالوگ انبار)؛ با هر باز کردن/ذخیره فهرست، اگر منبع اصلی تغییر کرده باشد همگام می‌شوند (امضا در `bot_settings.site_stock_lists_signature`). تخصیص‌های خودکار قدیمی سفارش کار در فهرست موجودی روزانه نمایش داده نمی‌شوند؛ تخصیص دستی کاربر (منوی تخصیص) کنار فهرست می‌ماند. منبع اصلی تغییر نمی‌کند.
- تست: `python scripts/smoke_site_stock_lists.py`.

نمونه Excel قدیمی `01_tank_consumption.xlsx` هنوز برای تحلیل مصرف تاریخی/آفلاین موجود است؛ مسیر UI تکنسین دیگر آپلود آن نیست.

- تشخیص: اول قواعد فارسی (نرمال‌سازی ی/ي، ک/ك، ارقام ۰-۹/٠-٩، نیم‌فاصله)؛ فقط اگر قواعد چیزی نیافتند Ollama با `format: json`، دمای ۰ و چند مثال (مناسب `qwen2.5:1.5b`). پارامترهایی که مدل برمی‌گرداند باید در خود سؤال باشند. اگر Ollama خاموش باشد مسیر قواعد پاسخ می‌دهد.
- نام مبهم (مثلاً «نازل پایینی چنجر») → فهرست کدها به‌صورت دکمه.
- بازنویسی روان پاسخ با مدل (اختیاری، ⚙️ ← 🤖 دستیار ← «✍️ بازنویسی روان پاسخ»): فقط وقتی همهٔ اعداد خروجی دقیقاً همان اعداد متن قالبی باشد؛ وگرنه متن قالبی.
- ربات: وقتی مالک دستیار را فعال کند دکمهٔ «🤖 از دستیار بپرس» در منوی اصلی می‌آید؛ متن آزادی که با هیچ دکمه/مرحله‌ای جور نشود و پیام صوتی (Whisper) هم به دستیار می‌رود. پاسخ متنی + صدای Piper (اگر نصب باشد). وب: `/assistant` (متن یا فایل صوتی). هر پرسش در «📋 فعالیت کاربران» ثبت می‌شود (نیت و متن سؤال، بدون توکن).
- فعال‌سازی فقط با مالک و دیگر به نصب Ollama/Whisper وابسته نیست (بدون آن‌ها فقط قواعد متنی). نصب روی سرور (حتی از ایران): `sudo bash install.sh --with-assistant` یا بستهٔ آفلاین `--assistant-offline` (DEPLOY.md، «دستیار هوشمند صوتی»).
- تست: `python scripts/smoke_assistant.py` (قواعد، بازگشت مدل شبیه‌سازی‌شده، سیم‌کشی ربات/وب)؛ با دادهٔ واقعی: `python scripts/smoke_assistant.py --db data/bot.db` (کپی موقت؛ فایل اصلی نوشته نمی‌شود) و با مدل واقعی `--ollama-model qwen2.5:1.5b`.
